# nthpartyfinder — project rules

- Bare `cargo` on this machine is wrapped through Socket Firewall (`sfw` — supply-chain network filter) via a scoped zshrc function. Fixed 2026-06-11: `NO_PROXY=localhost,127.0.0.1,::1` exempts loopback (wiremock tests pass through the wrapper), and never-network subcommands (`fmt`/`clean`/`--version`) skip the ~0.4s wrapper overhead. If sfw ever wedges again (symptom: 405 "Socket Firewall Connection Required" on local test servers, or hanging live-network tests), fall back to `~/.cargo/bin/cargo` and check the proxy env it injects with `sfw sh -c 'env | grep -i proxy'`.
- **⚠️ `cargo test --lib` through the sfw wrapper REPORTS A FALSE GREEN. Never trust it for a full-suite result.** Observed 2026-07-29: the run dies partway (390 of 4,395 tests emitted) when a test resolves a deliberately-nonexistent name, the wrapper prints `Socket Firewall encountered an unexpected error: getaddrinfo ENOTFOUND trust.nonexistent.invalid.domain.test`, and the process **exits 0 with no `test result:` line at all**. A suite that stopped at 9% is indistinguishable from a passing one if you only read `$?` — and this survives the "never read an exit code through a pipe" rule, because the exit code itself is the lie. Proof: with a deliberate mutant in `dns.rs`, `cargo test --lib` exited 0 while the targeted run of the same test reported FAILED.
  - **Always run the full suite as `~/.cargo/bin/cargo test` (the real binary), and confirm a `test result: ok. N passed` line with N in the thousands.** Absence of that line is a failed run, whatever the exit code says.
  - Targeted runs (`cargo test --lib <filter>`) are safe through the wrapper — they don't reach the offending test — and are fine for tight iteration.
- **The project ISA at `./ISA.md` is the system of record** — read it at task start (criteria, decisions, verification history, open follow-ups TF-RERUN/TF-COV/TF-SLSA/TF-CATO/TF-SILENT).
- **Run `cargo test` from `nthpartyfinder/`** (the crate dir), not the repo root.
- No live DNS in the unit/integration suite (wiremock only; live smoke tests are `#[ignore]`-gated). DoH endpoints must serve the JSON GET API (`application/dns-json`) — verify any new provider live before adding it.
- DNS failure-visibility contract: provider failures are classed (`DNS_THROTTLE` = 429/5xx with backoff+rotation; `DNS_ENDPOINT` = 4xx/bad-RCODE/non-dns-json with immediate rotation), counted at the `note_throttle` choke point for the exit-3 guard, and logged warn-once-per-provider. Don't add code that converts a provider error into an empty result without classification + counting.
- Logging goes through tracing (subscriber initialized in `app.rs`, default WARN, `-v` INFO, `-vv` DEBUG) and is emitted via `logger::ProgressAwareWriter` — bar-safe on TTYs, plain stderr otherwise. `AnalysisLogger::warn` prints at default verbosity; don't re-gate it.
- A second `--init` refuses to overwrite an existing config by design.
- **No wrapper scripts for scan safety — ever. (Owner directive, 2026-07-18.)** `scripts/safe-scan.sh` was a temporary, deliberately-superseded measure and has been removed from the repo. Every safety mechanism (FD-limit self-raise, connection/browser/subfinder concurrency bounds, startup orphan-process sweep) lives in the binary itself (`app::raise_open_file_limit`, `http_client`'s connection ceiling, `browser_pool`/`discovery::subfinder`'s concurrency caps + `sweep_orphaned_chrome`/`sweep_orphaned_subfinder`) and runs unconditionally at startup — the raw binary invoked directly (`./target/release/nthpartyfinder …`) is the only supported invocation. Never suggest, write, or reintroduce an external safety wrapper; any new safety concern must be fixed inside `nthpartyfinder`'s own source, not bolted on around it.
- **Proactively triage open Dependabot/security-bot PRs and alerts every time you're doing any work in this repo — don't wait to be asked. (Owner directive, 2026-08-01, after 13 green PRs sat unmerged for a week.)** At the start of substantive work here, run `gh pr list --author app/dependabot --state open` and `gh api repos/grcengineering/nthpartyfinder/dependabot/alerts --jq '[.[]|select(.state=="open")]'`; if anything is open, handle it before or alongside the requested task rather than leaving it for a separate ask. Two tiers, matching `.github/workflows/dependabot-auto-merge.yml`'s own gate: (1) patch/minor cargo bumps and any docker/github-actions bump — these auto-merge on green CI without you; if one is still open and CI is green, just merge it, the automation isn't broken, it just hasn't run yet on an old PR. (2) major cargo bumps, npm bumps (frontend has zero CI coverage — see the workflow's own comment; build+smoke-test the frontend yourself before merging one), and actual Dependabot/CodeQL security alerts — these need real judgment: read the changelog/advisory, fix the code if it's a vulnerability (never suppress a scanner finding — same zero-tolerance rule as everywhere else), and verify before merging. `security-pr-tracker.yml` files/refreshes a tracking issue titled "Security items waiting on a human" when this tier has a backlog — check it, don't just wait for it to page you.
- **A merge completed under `GITHUB_TOKEN` (i.e. `gh pr merge --auto` from inside a workflow) will NOT trigger push-based CI on the resulting master commit — this is a known, accepted tradeoff, not a bug to route around with a stored credential.** Confirmed 2026-08-02, not theorized: GitHub's own anti-recursion policy suppresses `on: push` workflows for GITHUB_TOKEN-authored pushes; 4/4 same-day auto-merges hit it, 0/2 human-merged commits did. The fix that would eliminate it — authenticate the merge with a stored fine-grained PAT instead — was proposed and **explicitly rejected by the owner (2026-08-02): a long-lived secret sitting in the repo indefinitely is a materially worse blast radius than GITHUB_TOKEN's few-minute lifetime, and that tradeoff is not worth making for this.** `GITHUB_TOKEN` stays exactly as GitHub generates it everywhere in this repo — never add a PAT/`MERGE_TOKEN`-shaped secret to "fix" this. `ci-completeness-monitor.yml` runs on a 23-minute schedule (deliberately not push-triggered, since the whole failure mode is push-triggering silently not working) to detect this — comparing master's real tip-changes (via the Activity API's `pr_merge`/`push` events, NOT `/commits?sha=master`, which pollutes with non-tip ancestor commits pulled in by a plain `--merge`) against the always-on workflow set — and re-fires anything missing via `workflow_dispatch` (added to build/codeql/docker/security/scorecard.yml for exactly this). Gaps accumulate in an append-only tracking issue ("CI completeness gaps (recurring log)") rather than overwriting, so a pattern across occurrences stays visible — this org is on GitHub's Free plan, so the audit-log API that could otherwise help diagnose a recurrence 404s here. If you see this issue open: check whether the listed commit(s) were auto-merged before assuming anything new is wrong.
